<Callout type="info" title="Current runtime mode">
  Netdata is the only always-on observability runtime. SigNoz and its collection
  agent are stopped; their volumes and reviewed deployment code are retained for
  an explicit diagnostics session.
</Callout>

## Signal ownership

| Signal                                                               | Source of truth                      | Retention or fallback                 |
| -------------------------------------------------------------------- | ------------------------------------ | ------------------------------------- |
| Host CPU, load, memory, disk, filesystem, network, pressure, and OOM | Netdata native host collectors       | Bounded Netdata DBEngine              |
| Docker state, health, and container CPU, memory, and I/O             | Netdata Docker and cgroup collectors | Docker CLI for current state          |
| PostgreSQL health, transactions, locks, WAL, and query activity      | Netdata PostgreSQL collector         | PostgreSQL native views               |
| Airflow scheduler, executor, DAG-run, and task timers                | Airflow StatsD in Netdata            | Airflow metadata for semantic history |
| Internal HTTP health and public certificate validity                 | Netdata `httpcheck` and `x509check`  | Direct origin and edge checks         |
| Airflow task logs                                                    | Airflow UI and S3                    | S3 is durable                         |
| Service logs                                                         | Docker logs and systemd journal      | No centralized log archive            |
| Application traces and centralized WARN/ERROR logs                   | On-demand SigNoz only                | Not collected in steady state         |

Observability never defines workflow success and must not block Airflow, data processing, analytics,
OCR, or application serving.

## Access and security

The dashboard is `https://netdata.tgblab.io.vn`, protected by Cloudflare Access. The Agent binds
only to `127.0.0.1:19999` on `tgbao-dev-services`; port 19999 is not exposed publicly or through the
tailnet. StatsD binds only to `172.24.0.1:8125`, and the host firewall accepts UDP only from the
`lakehouse-observability` bridge.

The Agent is unclaimed and does not use Netdata Cloud. Anonymous telemetry, streaming, exporting,
and bearer protection for the ordinary dashboard are disabled. Sensitive PostgreSQL Functions and
the Health Management API use Agent-generated keys stored only in the persistent Netdata volume.
Never print, copy into Git, or place either key in a URL.

## Deploy and verify

Changes under `sysops/netdata/` run the path-scoped `deploy-netdata.yml` workflow after they reach
`main`. The workflow deploys the reviewed upstream digest over Tailscale, reconciles PostgreSQL
monitoring and the StatsD firewall, recreates only the Netdata project, and verifies collectors,
units, Functions, MCP, Health mode, mounts, and listener boundaries.

<Steps>
  <Step>
    Validate locally before pushing.

    ```bash
    make netdata-validate
    make check
    ```

  </Step>
  <Step>
    Confirm the runtime and identity on the services host.

    ```bash
    tailscale ssh ubuntu@tgbao-dev-services \
      'docker ps --filter label=com.docker.compose.project=netdata --format "{{.Names}} {{.Status}}"'

    tailscale ssh ubuntu@tgbao-dev-services \
      'curl -fsS http://127.0.0.1:19999/api/v1/info | jq "{version, mirrored_hosts}"'
    ```

  </Step>
  <Step>
    Inspect active alerts, resource use, and recent collector errors.

    ```bash
    tailscale ssh ubuntu@tgbao-dev-services \
      'curl -fsS "http://127.0.0.1:19999/api/v1/alarms?active" | jq ".alarms | length"'

    tailscale ssh ubuntu@tgbao-dev-services \
      'docker stats --no-stream netdata-netdata-1'

    tailscale ssh ubuntu@tgbao-dev-services \
      'docker logs --since 30m netdata-netdata-1 2>&1 | grep -Ei "error|failed" | tail -100'
    ```

  </Step>
</Steps>

Use the dashboard's Metrics, Nodes, Containers, Alerts, Live Views, and PostgreSQL Functions before
adding a custom chart. Inspect the context and unit contract directly when a value is surprising:

```bash
tailscale ssh ubuntu@tgbao-dev-services \
  'curl -fsS http://127.0.0.1:19999/api/v1/charts | jq -r ".charts[] | [.context, .units] | @tsv" | sort -u'
```

## Units and interpretation

| Quantity            | Netdata representation                                                                  |
| ------------------- | --------------------------------------------------------------------------------------- |
| Host CPU            | Percentage of total host capacity, bounded to 0-100%                                    |
| Container CPU       | `cgroup.cpu`; 100% means one logical core and a container may exceed 100%               |
| CPU quota           | `cgroup.cpu_limit`; percentage of the configured limit, not core consumption            |
| Memory              | MiB/GiB for bytes; percent only when a host-total or container-limit denominator exists |
| Filesystem capacity | GiB plus utilization percentage, kept separate by mount                                 |
| Disk throughput     | Native KiB/s                                                                            |
| Network throughput  | Native kilobits/s; do not compare directly with bytes/s                                 |
| Airflow duration    | Milliseconds; `Observed ... (p95)` is meaningful only when events occurred              |

Negative write or transmit dimensions show chart direction, not negative activity. An idle StatsD
timer interval is rendered as zero; it is not a zero-duration task observation.

## Alerts and noise control

The native Health engine and transition history stay enabled, but every external notification
transport is `NO`. A warning in the UI is therefore diagnostic state, not evidence that a page was
sent. Calculation helpers may be `UNDEFINED` after restart or without enough history; investigate
the associated chart before treating them as collector failures.

The only repository-owned health override is PostgreSQL aborted-transaction ratio: it evaluates a
five-minute average each minute, enters warning above 2%, recovers at or below 1%, and routes to the
`dba` role when notification delivery is eventually configured. Keep stock alerts unless measured
noise demonstrates a specific bad threshold. Do not silence all cgroups, container health, or host
load to hide one noisy workload.

Before enabling notifications:

1. Observe warning and critical transitions across normal workload cycles.
2. Define one owner and receiver for disk/inode pressure, memory/swap/OOM, sustained CPU/load or
   I/O pressure, unhealthy containers, endpoint failures, and Agent-data absence.
3. State the signal, window, threshold, recovery condition, and unit in each override.
4. Test one controlled transition and recovery without adding duplicate SigNoz routing.

## Retention and capacity

The Agent uses DBEngine with three combined time-and-size ceilings:

| Tier | Resolution | Time ceiling | Size ceiling |
| ---- | ---------- | ------------ | ------------ |
| 0    | 1 second   | 7 days       | 1 GiB        |
| 1    | 1 minute   | 90 days      | 1 GiB        |
| 2    | 1 hour     | 1 year       | 512 MiB      |

The size limit can shorten the time window and is the safety boundary. The accepted v2.10.4 runtime
had 984 charts and 2,862 dimensions, averaged about 1.44% of one logical core, peaked near 2.33%,
used roughly 84-87 MiB internally, and held about 263 MiB of cache after the four-hour comparison.
The container remains capped at 0.5 CPU and 512 MiB. Revisit retention only from longer steady-state
disk evidence, while preserving at least 20 GiB free disk and 20% free host RAM.

```bash
tailscale ssh ubuntu@tgbao-dev-services \
  'docker exec netdata-netdata-1 du -sh /var/cache/netdata /var/lib/netdata'
```

## Upgrade and rollback

The reviewed release is the versioned, multi-architecture digest in `sysops/netdata/image`; never
replace it with `latest` or an unpinned channel. For an upgrade, review upstream release notes and
the image manifest, change only the reviewed reference and required configuration, run the local
validation, then let the Netdata workflow deploy it. Confirm version, alerts, collector errors,
history, and resource limits after recreation.

Rollback by reverting the complete Netdata release commit and manually dispatching
`deploy-netdata.yml`. Preserve `netdata-lib` and `netdata-cache` when the versions are storage
compatible. If an incompatible database migration prevents startup, Netdata history may be
discarded and rebuilt; application recovery must never depend on it.

## Backup and recovery

Netdata's metric database is disposable operational history, not business data and not a backup.
Git owns collector, alert, retention, and deployment configuration. No separate Netdata volume
backup is required. Recreating the Agent must preserve workload availability even when its history
is deliberately discarded.

Airflow logs remain in S3, metadata PostgreSQL uses its own checked backups, and lakehouse data is
recovered with S3 and Iceberg catalog metadata together.

## Troubleshooting

| Symptom                                   | First checks                                                                            | Likely boundary         |
| ----------------------------------------- | --------------------------------------------------------------------------------------- | ----------------------- |
| Dashboard is unreachable                  | Container health, loopback API, Cloudflare Tunnel, Access policy                        | Netdata or edge         |
| A chart disappeared                       | Collector logs, source service state, context in `/api/v1/charts`                       | Native collector        |
| Airflow charts are empty                  | Scheduler/DAG processor health, StatsD socket, firewall chain, bounded metric allowlist | Airflow StatsD path     |
| PostgreSQL charts are empty               | Metadata container, `pg_monitor` secret/role, Docker discovery, `pg_stat_statements`    | PostgreSQL collector    |
| Container CPU exceeds 100%                | Confirm `cgroup.cpu`; divide by 100 only when reasoning in logical cores                | Expected unit semantics |
| Certificate succeeds but origin fails     | Compare `x509check` with the corresponding loopback `httpcheck`                         | Edge versus origin      |
| Many alerts are `UNDEFINED` after restart | Allow history to accumulate; inspect whether the source chart exists                    | Calculation warm-up     |
| Agent approaches its limit                | Chart cardinality, enabled collectors, cache tiers; do not raise limits first           | Netdata scope/retention |

## On-demand SigNoz

SigNoz is retained only for an incident that explicitly requires centralized logs, traces, or its
APM workflow. Pull requests still validate Foundry, Collector, dashboards, and alerts, but pushes do
not deploy it. Start or update the stack only by manually dispatching `deploy-signoz.yml`; that
workflow deploys SigNoz and the Collector before applying Terraform-managed dashboards and alerts.

When the diagnostic session ends, stop both Compose projects on the host without deleting volumes:

```bash
docker ps --filter label=com.docker.compose.project=signoz --format '{{.Names}}' \
  | xargs -r docker stop
docker ps --filter label=com.docker.compose.project=signoz-collection-agent --format '{{.Names}}' \
  | xargs -r docker stop
```

The dormant UI hostname remains `https://observe.tgblab.io.vn`; an unavailable origin is expected
while the stack is stopped. Do not edit Terraform-managed SigNoz dashboards or alerts in the UI.
